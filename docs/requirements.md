# 登録サービス棚卸しツール 要件・仕組み（ローカル完結型）

## 目的
- 過去に登録したWebサービスを一覧にし、不要なアカウントを退会することで、情報漏洩リスクを減らす
- ユーザーのメールデータを第三者（開発者を含む）に一切渡さない

## 基本方針
- 処理はすべてブラウザ内で完結させる（サーバーへのアップロード、外部API、アクセス解析を一切使わない）
- 「通信していないこと」をユーザー自身が検証できるようにする
	- CSPで `connect-src 'none'` を指定し、外部通信を技術的に禁止する
	- ソースをOSSとして公開する
	- 一度読み込めばオフラインでも動作する（PWA）
- Gmail APIは使わない（Google審査・CASAの対象外にするため）

## 入力
- 必須：メールのエクスポートファイル（mbox）
	- 想定はGoogleテイクアウトのGmail mbox
	- ラベルを指定して部分的にエクスポートしたものにも対応する
	- 他のメールサービスのmboxも同じ仕組みで扱える
- 任意：パスワードマネージャのエクスポートCSV
	- Chrome、Bitwarden、1Passwordなど
	- 読み取るのはURL列のみ。パスワード列は読み込んだ直後に破棄し、保持しない
- 任意：手動での追加入力（ソーシャルログインの連携先など、メールに残っていないもの）

## 処理の流れ
1. 読み込み
	- `File.stream()` でチャンク単位に読む（数GBのファイルでも全体をメモリに載せない）
	- Web Workerで処理し、UIを固めない
	- 進捗をバイト数ベースで表示する
2. mboxの分割とヘッダーの抽出
	- `From ` で始まる行をメッセージの区切りとして扱う
	- 読むのは From / Subject / Date / List-Unsubscribe など必要なヘッダーだけ
	- 本文はスキップする（解析もしないし保持もしない）
	- MIMEエンコードされた件名をデコードする（RFC 2047、ISO-2022-JP / UTF-8 / Shift_JIS）
3. 送信元の正規化
	- From のアドレスからドメインを取り出す
	- Public Suffix Listを使って登録可能ドメインに丸める（例：mail.example.co.jp → example.co.jp）
	- 別名辞書で同じサービスにまとめる（例：amazon.co.jp と amazon.com）
4. シグナルの判定（件名のキーワード・正規表現によるスコアリング）
	- 登録系：会員登録 / 仮登録 / 本登録 / 登録完了 / ようこそ / メールアドレスの確認 / welcome / verify
	- 利用系：ログイン通知 / パスワード再設定 / 二段階認証 / 注文確認
	- 退会系：退会完了 / アカウント削除 / 解約 → 「退会済み候補」として印を付ける
	- 配信系：List-Unsubscribe ヘッダーだけがあり、上記のどれにも当たらない → メルマガのみの可能性（アカウントの有無は不明）
5. 集約
	- ドメインごとに、初回受信日・最終受信日・件数・検出したシグナルの種類・代表的な件名を集める
	- パスワードマネージャのURLと突き合わせ、検出元（メール / パスワードマネージャ / 両方）を記録する
6. 出力
	- 一覧表を表示する（並べ替えとフィルタができる）
		- 既定の並び順：アカウントの可能性が高い順、かつ最終受信日が古い順
	- 各行でユーザーがステータスを設定する：退会する / 残す / 退会済み / 対象外
	- 既知のサービスには退会ページへのリンクを表示する
	- 結果をCSV / JSONでエクスポートできる

## データの保持
- 初期設定は保存なし（タブを閉じれば消える）
- 任意で、作業途中の状態をIndexedDBに保存できる（明示的に有効にした場合のみ。削除ボタンも置く）
- 保存するのは集約後のデータのみ（ドメイン、日付、件数、代表的な件名）。生のメールは保存しない

## 退会リンクのデータベース
- 静的JSONとしてアプリに同梱する（実行時に取得しない）
- 既存の公開データセットを流用するかは、ライセンス確認後に判断する
- 日本のサービスは既存データの網羅性が低い見込みなので、自前で追加していく

## 技術構成（案）
- TypeScript + Vite で静的サイトとして作る
- 解析はWeb Workerで行う
- ホスティングはGitHub PagesまたはCloudflare Pages（静的配信のみ）
- 依存ライブラリを最小限にする（サプライチェーンのリスクを減らすため。ビルドの再現性も確保する）

## 非機能要件
- 数GBのmboxを一般的なPCで処理できること（目標値は検証してから決める）
- 外部へのリクエストがゼロであること（CIのE2Eテストでネットワークリクエストを監視して保証する）
- 対象はPCブラウザ（スマホは対象外。テイクアウトのファイル扱いが現実的でないため）

## 既知の限界
- 削除済みのメール、別のアドレスで登録したもの、電話番号だけで登録したものは検出できない
- ソーシャルログインで登録した場合、確認メールが来ないサービスがある
- 件名のルールによる判定には誤検出と見逃しがある（最終判断はユーザーが行う）
- 送信元ドメインがブランド名と一致しないサービスがある（配信代行サービスや親会社のドメインなど）

## MVPの範囲
- mboxの読み込み → ヘッダーの抽出 → ドメインでの集約 → シグナル判定 → 一覧表示 → CSV出力
- 後回しにするもの：パスワードマネージャCSVとの突き合わせ、退会リンクDB、IndexedDBへの保存、PWA化
